## 1. 設計方針

| 方針 | 内容 |
|---|---|
| サーバー権威 | ゲームの状態・時間・勝敗はすべてサーバーが管理する。クライアントは表示と入力のみ |
| 秘匿情報の最小送信 | 各クライアントには、そのプレイヤーが見てよい情報だけを送る（ビュー生成をサーバーで行う） |
| NPCも同じ口から | NPCの行動は人間と同じ「アクション」としてルームに入力される。ゲームロジックは人間／NPCを区別しない |
| 小さく始める | 単一リージョン・単一サーバー構成から始め、ルーム単位で水平分割できる形にしておく |
| 設定の外出し | タイマー、閾値、モデル名、コスト上限は設定で変更可能にする |

## 2. 技術選定

| 領域 | 選定【案】 | 理由 |
|---|---|---|
| 言語 | TypeScript（全体） | フロントとサーバーで型・ゲームロジックの型定義を共有できる |
| フロントエンド | Next.js（React） | 画面数が少なく、SSRと静的配信の両方が使える。スマホ対応が容易 |
| UIライブラリ | Tailwind CSS | 速度重視 |
| サーバー | Node.js ＋ Fastify | 軽量。HTTP APIとWebSocketを同一プロセスで扱える |
| リアルタイム通信 | WebSocket（`ws`＋独自の薄いプロトコル） | イベント数が少なく、再接続・ルーム管理を自前で制御したい |
| DB | PostgreSQL | シナリオ・履歴などの関係データ、JSONB（カード等） |
| キャッシュ・状態保持 | Redis | 進行中ルームのスナップショット、マッチング待機、通報カウント、レート制限 |
| ORM | Prisma | 型安全、マイグレーション管理 |
| AI | Claude API（Anthropic SDK） | NPC発言には低コストの軽量モデル、投稿チェックには高精度モデルを使い分ける（§8.6） |
| 認証 | メール＋パスワード、Google ログイン | 仕様の【仮】に対応。セッションはHTTP-onlyクッキー |
| ホスティング | コンテナ実行環境（例：Cloud Run / Fly.io）＋マネージドDB／Redis | WebSocketの長時間接続に対応できるもの。固定IP・スティッキー接続は不要（§3.2） |
| CI | GitHub Actions | ビルド・テスト・マイグレーション検証 |

## 3. システム構成

### 3.1 全体図

```
[ブラウザ]
  │  HTTPS (REST)           WSS (ゲーム通信)
  ▼                          ▼
[Web: Next.js] ───────→ [Game/API サーバー (Fastify)]
                              │  ├─ REST API（認証・投稿・履歴・通報）
                              │  ├─ WebSocket Gateway
                              │  ├─ Room Manager（ルーム状態機械）
                              │  ├─ Matchmaker
                              │  ├─ NPC Engine ───→ [Claude API]
                              │  └─ Scenario Checker ─→ [Claude API]
                              ▼
                   [PostgreSQL]   [Redis]
```

### 3.2 ルームの配置

- 1つのルームは、**生きている間は1つのサーバープロセス上**で動かす（ルームの所有者）。
- ルームIDからの所有者の特定は、Redisの「room:{id}:owner」キーで行う。
- WebSocket接続時、接続先サーバーがルームの所有者でない場合は、**所有者へ内部転送**（Redis Pub/Sub）する。これにより、スティッキー接続を必須としない。【案】
- MVPでは**サーバー1台**から始め、上記の転送は無効のままでよい（構造だけ用意する）。
- サーバーが再起動した場合：ルームのスナップショット（§6.5）から他のプロセスが引き継ぐ。

## 4. モジュール構成

```
/apps
  /web            … Next.js（G01〜G10）
  /server         … Fastify（REST＋WS）
/packages
  /shared         … 型定義、メッセージスキーマ、ゲーム定数
  /game-core      … ルーム状態機械（純粋関数。サーバー・テストから利用）
  /npc            … プロンプト構築、NPC行動決定
/scenarios        … 運営制作シナリオ（JSON）
（Prismaのスキーマ・マイグレーションは apps/server/prisma）
```

| モジュール | 責務 |
|---|---|
| `game-core` | 状態遷移、手札公開、投票集計、勝敗判定。**入出力・時間・AIに依存しない**純粋なロジック（テストしやすさのため） |
| `Room Manager` | ルームの生成・保持・タイマー駆動・スナップショット保存。`game-core`にイベントを与えて状態を更新する |
| `WebSocket Gateway` | 接続の認証、ルームへの紐付け、メッセージの検証、ビュー（§7.4）の配信 |
| `Matchmaker` | 待機キュー、人数・シナリオの組合せ、タイムアウトでのNPC補完 |
| `NPC Engine` | NPC席の行動をスケジュールし、Claude APIを呼び、アクションとしてルームに入力する |
| `Scenario Service` | 投稿の保存、状態管理、公開前チェック、プレイ済みの除外 |
| `Moderation Service` | 通報の受付、自動非公開、チャットの禁止ワード処理 |

### 5.3 インデックスと制約

- `PlayedScenario(user_id, scenario_id)`：シナリオ一覧で「未プレイのみ」を取得するために使用する。
- `Scenario(status, published_at)`：一覧表示。
- 犯人が1人のみ：`UNIQUE INDEX ON Character(scenario_id) WHERE is_culprit`。
- 捏造カードが1枚のみ・手札の種類が2+2：Card は scenario_id を持たないため、部分ユニークインデックスでは保証できない。シナリオ入力のスキーマ（zod）と seed／投稿の保存処理で検証する。
- 公開済みシナリオのCharacter/Cardの更新は、アプリ層で禁止（かつDBトリガーで拒否）。

### 5.4 Redisの利用

|---|---|---|
| `room:{id}:state` | ルームのスナップショット（JSON） | 終了後1時間 |
| `room:{id}:owner` | 所有サーバーID | ルーム存続中 |

| `rate:{userId}:*` | チャット・APIのレート制限 | 数秒〜数分 |

## 6. ゲームルームの状態遷移設計

### 6.1 状態

```
INTRO → CONFIRM → REVEAL(1) → TALK(1) → REVEAL(2) → TALK(2) → REVEAL(3) → TALK(3) → VOTE → RESULT → CLOSED
```

セット番号（1〜3）は `setNo` として別に持つ。マッチング（待機・NPCでの人数補完）はルームを作る前に行うため、ルームに待機状態は無く、**INTRO から始まる**（実装時に WAITING を除き、SET を REVEAL と TALK に分けた。進捗.md §5 参照）。

| 状態 | 次へ進む条件（いずれか） |
|---|---|
| INTRO | 全人間が「次へ」／60秒 |
| CONFIRM | 全人間が「準備完了」／3分 |
| REVEAL | 全席（NPC含む）が公開カードを選択／30秒（未選択は自動選択） |
| TALK | タイマー10分／全人間が「話し終えた」に同意（会話は2人1組。下記） |
| VOTE | 全席（NPC含む）が投票／2分（未投票は棄権） |
| RESULT | 30分で CLOSED（または Close） |

- 「次へ」「準備完了」「話し終えた」は**人間の席だけ**を待つ（NPCの入力は待たない）。公開カードの選択と投票は全席を待つため、NPC Engineが短い遅延（2〜10秒）で入力する。
- 人間が全員NPCに切り替わった場合は、`aborted` として CLOSED にする。
- **会話の組**：TALK 中の会話は2人1組。席 `s` のセット `n` の相手は `s XOR n`（セット1は 0-1・2-3、セット2は 0-2・1-3、セット3は 0-3・1-2）。発言には `scope`（`pair`＝TALK中の組の会話、`all`＝RESULT の感想戦）を持たせ、`projectView` が TALK までは自分の組の `pair` の発言だけを返す。**他の組の会話は RESULT 以降に開示する**。`Chat` は TALK（`pair`）と RESULT（`all`）で受け付ける。NPCは `all` の発言をしない。

### 6.2 game-coreのインターフェース

```ts
// 純粋関数。副作用なし
function reduce(state: RoomState, event: RoomEvent, now: number): {
  state: RoomState;
  effects: Effect[];   // 例：配信、タイマー設定、保存
}
```

- `RoomEvent`：`Join`, `Leave`, `Ready`, `PickCard`, `Chat`, `AgreeEndTalk`, `Vote`, `Tick(now)`, `SwitchToNpc(seat)` など。
- `Effect`：`Broadcast(view)`, `ScheduleTimer`, `Persist`, `RequestNpcAction(seat)` など。
- 時間は引数`now`として受け取る。これにより、テストで時間を自由に進められる。

### 6.3 タイマー

- 各状態の終了時刻（`deadlineAt`）を状態に持たせ、サーバー時刻を基準とする。
- 実際の駆動：Room Managerが `setTimeout` で `Tick` を発行する。サーバー再起動後は、スナップショットの`deadlineAt`から再設定する。
- クライアントにも`deadlineAt`と`serverNow`を送り、**差分で残り時間を表示**する（クライアント側の時計のずれに依存しない）。

### 6.4 無操作・切断の検知

- 各席に `lastActiveAt` を持たせる。更新対象：チャット、カード選択、投票、各種ボタン。ping/pongのみでは更新しない。
- 切断中も `lastActiveAt` は更新されない。
- `Tick`の際、`now - lastActiveAt ≥ 3分` の人間席を `SwitchToNpc` に変換する。切替の30秒前（2分30秒）に、本人へ警告イベントを送る。
- 例外：状態の締め切り待ちの間（全員の投票が終わって待機中など）は、判定の対象外とする。
- `SwitchToNpc`後、その席は `kind=npc` となり、NPC Engineの管理に入る。元のユーザーは**観戦モード**で接続を維持できる（自キャラの情報は閲覧可、操作不可）。

### 6.5 永続化と復旧

- 状態が変わるたびに、`room:{id}:state` を更新する（差分ではなくスナップショット）。
- ゲーム終了時、`Game`／`Participation`／`ChatMessage`／`RevealedCard`／`Vote`／`PlayedScenario`を**1トランザクション**でPostgreSQLに書き込む。
- チャットログのDB書き込みは、負荷軽減のため**ゲーム終了時にまとめて**行う。進行中の障害でログが失われる可能性は許容する。【案】
- 復旧：サーバー起動時にRedis上の未終了ルームを走査し、所有者がいないものを引き継ぐ。

### 6.6 プレイ済みの記録タイミング

- INTROからCONFIRMに遷移した瞬間に、人間の全席について `PlayedScenario` を書き込む（仕様7.3）。
- この書き込みは、状態遷移とは別に**即時**行う（ゲーム終了を待たない）。

## 7. リアルタイム通信設計

### 7.1 接続

1. クライアントが `wss://.../ws?roomId=...` へ接続し、セッションクッキーで認証する。
2. サーバーは、そのユーザーがルームの参加者かを検証する。参加者でなければ拒否。
3. 接続成功後、サーバーが**現在のビュー全体**（`snapshot`）を送る。再接続時も同じ。
4. 以降は、変更イベントを差分で送る。クライアントは`seq`番号の欠番を検知したら、`snapshot`を再要求する。

### 7.2 メッセージ形式

JSON。全メッセージに `type` と、サーバー→クライアントには `seq`（ルーム内の連番）を付ける。スキーマは `packages/shared` でzod等により定義し、双方で検証する。

**クライアント → サーバー**

| type | 内容 | 受付可能な状態 |
|---|---|---|
| `ready` | 「次へ」「準備完了」 | INTRO, CONFIRM |
| `pickCard` | `{cardId}` | SET.REVEAL |
| `chat` | `{body}` | TALK（組の相手に届く）、RESULT（全員に届く感想戦） |
| `agreeEndTalk` | | SET.TALK |
| `vote` | `{targetCharacterId}` | VOTE |
| `startNow` | 今すぐNPCで開始 | WAITING |
| `resync` | snapshot再要求 | 任意 |
| `ping` | | 任意 |

**サーバー → クライアント**

| type | 内容 |
|---|---|
| `snapshot` | 自分用ビュー全体（§7.4） |
| `phase` | 状態遷移（新しい状態、`deadlineAt`、`serverNow`） |
| `chat` | 発言（キャラクターID、本文、時刻） |
| `reveal` | 4枚の同時公開（カード内容を含む） |
| `seat` | 席の変化（NPC切替、接続／切断の表示） |
| `warn` | 無操作の警告（切替までの秒数） |
| `result` | 得票、勝敗、結末文、全員の手札（捏造カードの印つき） |
| `error` | `{code, message}` |

### 7.3 受付時の検証

すべてのクライアント発メッセージについて、サーバーは次を検証する。

1. スキーマが正しいか。
2. 現在の状態でそのメッセージが許されるか（例：投票はVOTE中のみ）。
3. 送信者の席が、そのアクションを実行できるか（観戦者は不可）。
4. 値の妥当性（`cardId`が自分の未公開の手札か、`targetCharacterId`が自分以外か、本文が200文字以内か）。
5. レート制限（チャット：1秒1件）。

違反は`error`で返し、状態は変えない。

### 7.4 ビュー生成（秘匿の保証）

`projectView(state, seat)` を `game-core` の関数として用意する。**これが、クライアントに送る唯一の経路**とする。

| 項目 | 本人 | 他の席 |
|---|---|---|
| 冒頭文、公開プロフィール（4人分） | ○ | ○ |
| 自キャラの状況文、手札4枚 | ○ | ✕ |
| 公開済みカード | ○ | ○ |
| 他キャラの状況文、未公開の手札 | ✕ | ✕ |
| 犯人が誰か | 犯人本人の席のみ ○ | ✕ |
| どのカードが捏造か（持ち主・タイトル・内容） | 犯人本人の席のみ ○ | ✕ |
| 結果（RESULT到達後）：犯人、全員の手札（捏造の印つき）、結末文 | ○ | ○ |

- RESULT到達前は、`Character.is_culprit`の情報をいかなるレスポンスにも含めない。
- RESULT到達前は、`Card.is_fabricated`を犯人の席以外に含めない。捏造カードの持ち主が探偵側でも、持ち主のビューには含めない。犯人の席には、他人の手札にある捏造カードも、未公開のうちから `fabricatedCard`（持ち主の席、タイトル、内容）として含める（仕様4.3.1）。
- 公開済みカード・手札の `kind`（種類）は、見えるカードについては全員に含めてよい。
- ビュー生成は専用のユニットテスト（§15）でカバーする。

### 7.5 再接続

- クライアントは、切断を検知したら指数バックオフ（1, 2, 4, …最大10秒）で再接続する。
- 再接続すると§7.1に従い`snapshot`が届く。切断中のチャットは`snapshot`内の履歴で補う。
- 同一席に新しい接続が来た場合は、**古い接続を閉じる**（複数タブ対策）。

## 8. NPC（AI）設計

### 8.1 NPC Engineの役割

- NPC席ごとに「次に何をするか」を決め、アクション（`chat`, `pickCard`, `vote`, `ready`）として Room に入力する。
- ルームにとってNPCは「少し遅れて操作する参加者」であり、特別扱いのコードは持たない。

### 8.2 発言のスケジューリング

- TALK状態のNPC席ごとに、**次回発言予定時刻**を持つ。基準は30〜60秒でランダム（仕様5.3）。話しかけられたら3〜6秒後に返事をする（待機中に話しかけられた場合も、予定を前倒しする）。
- 次の場合は予定を前倒しする：
  - 組の相手が最後に発言していて、自分がまだ返していない（2人1組の会話のため）。
  - 公開カードに自キャラの内容が含まれる。
- 次の場合は予定を後ろにずらす：直前に組の相手が発言した（直近5秒以内の発言があれば+5秒）。
- 発言を決定する際、**ルームの最新の状態を再取得**してAIを呼ぶ（古い状態での発言を防ぐ）。

### 8.3 プロンプト構成

NPC一回の呼び出しは、次の構成とする。

```
[system]
 役割：マーダーミステリーの参加者として振る舞う。
 ルール：発言は100文字以内、キャラクターの口調で。メタ発言（AI・プロンプトへの言及）禁止。
        他キャラの非公開情報を推測で断定しない。
        カード16枚のうち1枚だけが捏造（嘘の内容）。誰の手札にあるかは分からない。
 [犯人でない場合] 嘘をつかない。秘密は聞かれるまで言わなくてよい。
                  公開カード同士・自分の手札との矛盾を探す。自分の手札も、犯人に仕込まれた捏造の可能性がある。
 [犯人の場合]    自分が犯人であることを隠す。嘘・はぐらかしは可。
                  捏造カード（■ 捏造カード 参照）は、公開済みなら真実だと言い張る。それ以外の公開済みカードと矛盾する発言は禁止。

[user]
 ■ 冒頭文
 ■ 自分のキャラクター（名前、公開プロフィール、状況文、手札4枚＋種類＋公開済みか否か）
 ■ 捏造カード（犯人の場合のみ。持ち主、タイトル、内容、公開済みか否か）
 ■ 他のキャラクターの公開プロフィール
 ■ 公開済みカード（誰がどのカードを公開したか）
 ■ これまでの会話（直近30件）
 ■ 今回の指示：「次の発言を1つ出力」
 出力形式：JSON {"say": "..."}
```

- **与えない情報**：他キャラの状況文・非公開手札。犯人NPCにも「犯人であること」、自分の事実、どのカードが捏造かのみを与える（仕様5.2）。探偵側NPCには `is_fabricated` を渡さない（自分の手札が捏造でも）。
- システムプロンプトとシナリオ共通部分は**プロンプトキャッシュ**の対象とし、コストを抑える。
- 出力はJSONスキーマで検証し、不正な場合は1回だけ再試行する。2回失敗した場合は、「少し考えさせてください」等の定型文でつなぐ。

### 8.4 手札公開と投票

- **公開カード選択**：自キャラの未公開カードの一覧を渡し、`{"cardId": ...}`を返させる。犯人NPCには「自分に不利なカードは後に回す」「自分の捏造カードは、疑いをそらすのに役立つ時点で出す（出さなくてもよい）」ことを指示する。
- **投票**：公開カードと会話を渡し、`{"target": キャラクターID, "reason": "..."}`を返させる。`reason`は記録のみで、表示はしない。
- 失敗時のフォールバック：手札公開はランダム、投票は「自分以外で最も発言で名指しされた人」とする。

### 8.5 発言の安全対策

- 出力に、NPC自身の非公開情報の**丸写し**（状況文の長い一致）が含まれないかを簡易チェックする。【案】
- 出力に禁止ワードが含まれる場合は破棄して再生成する。
- 他キャラの非公開情報はそもそも渡していないため、NPCが漏らすリスクは設計で排除されている。

### 8.6 モデルの使い分けとコスト制御

| 用途 | モデル【案】 | 理由 |
|---|---|---|
| NPC発言・手札選択・投票 | `claude-haiku-5-5` | 低コスト・低遅延 |
| 投稿時の整合性・不適切表現チェック | `claude-sonnet-5-5` | 推理可能性の判定に精度が必要 |

- 評価（S3）の結果次第で、NPCの犯人役・投票のみ上位モデルに切り替える。
- **ゲームごとのコスト予算**を持ち、累計トークンが80%を超えたら発言間隔を長くし、100%で定型文のみにする。
- 設定値：最大出力トークン、直近履歴の件数、発言間隔、予算。

### 8.7 NPCの待ち時間の隠蔽

- 発言生成の前に、人間のように「入力中…」を2〜4秒表示する。生成が間に合わない場合は、そのまま待たせる。
- 実装：`NpcTyping` 操作でルームの `typing`（考え中のNPC席）を更新し、`projectView` が**いまの会話の相手のNPCについてだけ** `partnerTyping` を返す。生成と最低待ち時間（2〜4秒）の長いほうが終わったら発言し、`typing` は発言またはフェーズ移行で消える。
- AI APIがタイムアウト（15秒）した場合は、スキップして次回の予定を再設定する。

## 9. シナリオ投稿・AIチェック設計

### 9.1 投稿の流れ

```
下書き保存（随時）→ 「公開」操作 → 構造チェック（同期）
   → AIチェック（非同期、最大30秒）→ 結果表示
   → [不適切表現なし] 公開確認 → status=published
```

- AIチェックはジョブとして実行し、クライアントは結果をポーリング（2秒間隔）で取得する。
- 公開時、`content_version`を採番し、以後は本文の変更を受け付けない。

### 9.2 チェック処理

1. **構造チェック**（コードで実施）：必須項目、文字数、犯人1人、カード16枚、各キャラクターの手札が目撃証言2枚・証拠品2枚、捏造カード1枚。
2. **不適切表現チェック**（AI）：カテゴリ別の判定（残虐／性的／実在人物・団体の誹謗／差別）を、JSONで返させる。1つでも該当で公開不可。
3. **整合性チェック**（AI）：全情報を渡し、以下を判定する。
   - 犯人を、カードと状況文から**推理で特定できるか**（根拠のカードを挙げさせる）。
   - 犯人以外にも、同程度に疑わしい人物がいないか。
   - 捏造カードが、真実のカード1枚と直接矛盾し、他の情報から見破れるか（仕様6.2.1）。
   - 結末文が、カード・状況文と矛盾しないか。
   - 結果：`ok | warn`＋指摘リスト。`warn`でも公開できる（仕様6.3）。

- 結果は `Scenario.check_result`（JSONB）に保存し、投稿者に表示する。
- 同一内容の再チェックはハッシュで検知し、キャッシュ結果を返す（コスト削減）。

### 9.3 一覧取得

- 「未プレイのみ」：`status=published` かつ `PlayedScenario`に該当しない、かつ`author_id != 自分`。
- 表示順：公開日の新しい順（MVP）。

## 10. API設計

REST。JSON。エラーは `{code, message}`。

| GET `/auth/google` | ソーシャルログイン | なし |
| GET `/me` | 自分の情報 | ログイン |
| GET `/me/scenarios` | 自分の投稿一覧 | ログイン |
| POST `/scenarios` | 下書き作成 | ログイン |

| POST `/scenarios/:id/check` | AIチェック開始 | 投稿者 |
| GET `/scenarios/:id/check` | チェック結果の取得 | 投稿者 |

| POST `/scenarios/:id/hide` | 非公開 | 投稿者 |
| GET `/scenarios/available` | 未プレイの公開シナリオ一覧 | ログイン |
| GET `/scenarios/:id` | 詳細（概要のみ。真相は含まない） | ログイン |
| POST `/matches` | `{scenarioId, size}`でマッチング参加 → `{matchId}` | ログイン |

- マッチング成立の通知は、WebSocketの専用接続（`/ws/lobby`）で送り、`roomId`を返す。クライアントは`roomId`で`/ws`へ接続する。
- `GET /scenarios/:id` は、**本文（状況文・手札・結末文）を一切返さない**。ゲーム外から真相を取得できないようにする。ただし投稿者本人の編集用エンドポイントのみ全項目を返す。

### 10.1 マッチングの詳細

- `POST /matches {size: 1}`：即時に`Game`を作成し、NPC3席で開始。
- `size 2〜4`：Redisのキュー `mm:queue:{scenarioId}:{size}` に追加。人数が`size`に達したらルームを作成。
- 待機90秒が経過、または`startNow`：その時点の参加者でルームを作成し、不足席をNPCで補う。
- 同じシナリオをプレイ済みの人は、キューに入る時点で拒否される（API側でチェック）。

## 13. エラー処理・耐障害性

| 事象 | 対応 |
|---|---|
| クライアント切断 | 再接続を許可。5.4の無操作時間でNPC切替 |
| 全人間が離脱 | NPCだけで進行を続けず、**ゲームを`aborted`として終了**（AIコスト防止）。プレイ済みは維持 |
| AI APIの失敗・遅延 | 再試行1回→フォールバック（定型文／ランダム選択）。ゲームを止めない |
| AI APIの全面障害 | NPCを含むマッチングを一時停止し、全員人間のマッチング（2〜4人指定）のみ受け付ける。画面に告知 |
| サーバー再起動 | Redisのスナップショットから復旧（§6.5） |
| DB書き込み失敗（ゲーム終了時） | リトライキューに入れ、成功するまで再試行。結果画面は先に表示する |
| 二重操作（二重投票など） | unique制約と状態検証で冪等にする |
