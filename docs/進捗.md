## 1. 運用ルール

### 1.1 記録のルール
- 作業を終えるたびに、本書を更新する（§4 作業ログ、§2 サイクル状況）。
- 本書の更新は、**その作業のコミットに含める**（コードと記録のずれを防ぐ）。
- 仕様・設計の変更が生じた場合は、**先に `仕様書.md` / `設計書.md` を更新**し、§5 に変更履歴を残してから実装する。
- 判断や不具合は §6 に残す。

### 1.2 Git／GitHub運用
| 項目 | ルール |
|---|---|
| ブランチ | `main`は常に動く状態を保つ。機能・サイクル単位の作業は `feat/<サイクル>-<内容>`、`fix/<内容>` で切り、PRで`main`へマージする。**文書の修正や小さな変更はPRを作らず、`main`へ直接コミットしてよい** |
| コミット | Conventional Commits（`feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`）。日本語の説明可 |
| コミット粒度 | 1つの意図につき1コミット。テストと実装は同じPRに含める |
| PR | 1サイクル内の機能単位（小さな変更では不要）。説明に「対応する仕様ID・設計の節・検証結果」を書く |
| Issue | サイクル（S0〜S7）ごとにマイルストーンを作り、機能・不具合をIssueで管理する |
| タグ | サイクル完了時に `s0-done` のようにタグを付ける。公開時は `v1.0.0` |
| CI | PRでビルド・テストが通ること（S0で整備） |
| 秘密情報 | APIキー等はコミットしない（`.env`は`.gitignore`済み） |
