# マーダーミステリー・オンライン 開発計画書

関連文書：`企画書.md`（企画内容・ゲームルール）

## 1. 目的と方針

企画書の内容を実現するため、**仕様書 → 設計書 → 実装 → 検証（反復）** の流れで開発を進める。

- 仕様・設計は実装前に固め、手戻りを減らす。
- 実装は機能単位の小さなサイクルで進め、**実装→検証を繰り返す**。
- 不確実性の高い要素（AI NPC）は早期に試作して検証する。
- 実装中に仕様・設計の不備が見つかった場合は、先に文書を更新してから実装に反映する。

## 2. 全体フロー

```
企画書 → 仕様書 → 設計書 → 実装 ⇄ 検証（反復） → βテスト → 公開
                    ▲                  │
                    └── 不備があれば文書を更新 ──┘
```

## 3. フェーズ別計画

| フェーズ | 内容 | 成果物 | 完了条件 |
|---|---|---|---|
| 1. 仕様策定 | 企画書をもとに機能・画面・ルールを詳細化 | 仕様書 | 全機能の入出力・条件・例外が文書化され、レビュー済み |
| 2. 設計 | 技術選定、構成、データ、通信、AI連携の設計 | 設計書 | 実装に着手できる粒度で、仕様書の全項目に対応している |
| 3. 実装・検証サイクル | 機能単位で実装し、都度検証 | 動作するアプリ、テスト | 各サイクルの完了条件を満たす（§5） |
| 4. 総合検証 | 全機能を通した結合・負荷・セキュリティ確認 | 検証報告書 | 重大不具合が0件 |
| 5. クローズドβ | 少人数の実プレイで体験とコストを確認 | 改善リスト | 完走率・満足度が目標値以上 |
| 6. 公開・運用 | 公開、監視、改善 | 運用手順書 | 公開 |

## 4. 作成する文書

### 4.1 仕様書（フェーズ1）
- 機能一覧と優先度（MVP / 将来）
- 画面一覧と画面遷移図（ホーム、投稿、シナリオ選択、ゲームルーム、投票、結果）
- ゲームルール詳細
  - 進行フローとタイマー（10分×3セット、投票2分）
  - 手札の同時公開、勝敗判定、同数時の扱い
  - 無操作判定時間と NPC への切替条件
  - プレイ済みシナリオの除外条件
- シナリオ投稿の入力項目・文字数上限・入力チェック
- NPC の振る舞い要件（発言頻度、犯人NPCの嘘、秘匿情報の扱い）
- 通報・非公開・モデレーションの運用ルール
- 非機能要件（同時接続数、応答時間、AIコスト上限、対応ブラウザ）

### 4.2 設計書（フェーズ2）
- システム構成図（フロント／API／リアルタイム通信／DB／AI API）
- 技術選定と理由（企画書の案を確定）
- データ設計（ユーザー、シナリオ、キャラクター、手札、ルーム、チャットログ、プレイ履歴、通報）
- ゲームルームの状態遷移設計（待機→開始→議論×3→投票→結果）
- リアルタイム通信設計（イベント一覧、再接続、切断・無操作検知）
- AI NPC 設計（プロンプト構成、キャラごとに渡す情報の範囲、コスト制御）
- API 設計、認証・認可、セキュリティ設計（秘匿情報を他プレイヤーへ送らない）
- テスト方針と環境構成（開発／検証／本番）

## 5. 実装・検証サイクル

機能を以下の単位に分け、各サイクルで「実装 → 検証 → 修正」を繰り返す。

| サイクル | 実装内容 | 主な検証項目 |
|---|---|---|
| S0 | 開発環境、CI、雛形作成 | ビルド・テストが自動で動く |
| S1 | アカウント、シナリオデータ構造、運営制作シナリオ1本の登録 | データが正しく保存・取得できる |
| S2 | ゲームルーム（4人、チャット、タイマー、手札公開、投票、結果） | 全員人間で最初から最後まで遊べる、秘匿情報が漏れない |
| S3 | AI NPC（発言生成、手札選択、犯人NPC） | 設定どおりの発言か、秘密を漏らさないか、コストが想定内か |
| S4 | 人数補完と無操作時のNPC切替、再接続 | 1〜3人でも開始でき、切替後も進行が止まらない |
| S5 | シナリオ投稿、AIチェック、プレイ済み管理 | 投稿→公開→プレイの一連が通る。再プレイ不可が守られる |
| S6 | 通報・自動非公開、運営画面 | 閾値超過で非公開になる |
| S7 | UI調整、スマホ対応、アクセシビリティ | 主要ブラウザ・端末で操作できる |

### 各サイクルの進め方
1. 仕様書・設計書の該当箇所を確認する。
2. 実装する（小さな単位でコミット）。
3. 検証する（§6）。
4. 不具合や仕様の不備を修正し、必要なら文書を更新する。
5. 完了条件を満たしたら次のサイクルへ。

### リリース候補の区切り

| 区切り | 範囲 | 内容 | 判断すること |
|---|---|---|---|
| **R1（最初のリリース候補）** | S0〜S4 | 運営制作シナリオのみ。1〜4人で、NPC補完・無操作切替・再接続まで遊べる | 遊びの核とNPCの品質・コストが成立するか。ここで少人数に遊んでもらう |
| R2 | S5〜S6 | シナリオ投稿、AIチェック、通報・自動非公開、運営画面 | 投稿の品質が保てるか。保てない場合は限定公開にする |
| R3 | S7 | UI調整、スマホ対応 | 公開（クローズドβ→公開）に進めるか |

- R1 の時点で、投稿機能は無い。シナリオは運営が用意し、データとして登録する。
- R1 の結果（完走率、満足度、AIコスト）をもとに、R2 以降の優先度を見直す。

> S3（AI NPC）は不確実性が高いため、S2 と並行して**プロンプトの試作と評価を先行**して行う。

## 6. 検証計画

| 種類 | 内容 | タイミング |
|---|---|---|
| 単体テスト | 勝敗判定、タイマー、手札公開、プレイ済み判定などのロジック | 実装と同時 |
| 結合テスト | API・リアルタイム通信・DBを通した一連の動作 | 各サイクル終了時 |
| ゲーム通しテスト | 実際に4人（人間／NPC混在）で1本を完走 | S2以降、毎サイクル |
| NPC品質評価 | 秘匿情報の漏洩有無、キャラ一貫性、犯人NPCの嘘の自然さを評価用シナリオで確認 | S3、プロンプト変更の都度 |
| 異常系テスト | 切断、再接続、全員離脱、無操作、同時操作 | S4 |
| 負荷・コスト検証 | 同時ルーム数、AI API の呼び出し量と費用 | 総合検証 |
| セキュリティ確認 | 権限チェック、入力検証、他人の手札が送信されないこと | 総合検証 |
| ユーザー検証 | 実プレイでの満足度、わかりにくい点の収集 | βテスト |

## 7. スケジュール（目安）

| フェーズ | 期間 |
|---|---|
| 1. 仕様策定 | 3週間 |
| 2. 設計 | 3週間 |
| 3. 実装・検証サイクル（S0〜S7） | 約4か月（1サイクル2〜3週間） |
| 4. 総合検証 | 3週間 |
| 5. クローズドβ | 4週間 |
| 6. 公開 | β終了後に判断 |

合計：公開まで約8〜9か月。体制や稼働時間により変動するため、フェーズ2終了時に再見積もりする。

## 8. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| NPCの品質が基準に届かない | 体験の低下 | S3を先行して試作・評価する。プロンプトと渡す情報の範囲を調整し、基準未達なら発言形式を制限する |
| AI APIのコスト超過 | 運営費の圧迫 | トークン上限・発言頻度の制御、軽量モデルの併用、同時ルーム数の上限設定 |
| 秘匿情報の漏洩（通信・NPC経由） | ゲーム性の破壊 | サーバー側で各プレイヤーに必要な情報のみ送信。NPCにも自キャラの情報のみ渡す |
| 投稿シナリオの品質低下 | 遊べない作品の増加 | AIチェックと通報による自動非公開、運営制作シナリオの併用 |
| 仕様変更による手戻り | 遅延 | 変更は仕様書・設計書を先に更新し、影響範囲を確認してから実装する |
| 初期のシナリオ不足 | 再プレイ不可で遊ぶものがなくなる | 公開前に運営制作シナリオを複数本（目標10本）用意する |

## 9. 管理方法

- 進捗は機能単位のタスクで管理し、各サイクル終了時に振り返る。
- 仕様書・設計書・コードはバージョン管理する（Gitを使用）。
- サイクルごとに動作する状態を保ち、いつでも通しプレイで確認できるようにする。
